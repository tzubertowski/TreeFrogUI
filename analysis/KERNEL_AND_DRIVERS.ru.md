## 1. Почему выбран запуск из RAM

Штатный `cubegm/vmlinux.uImage` находится в контейнере, механизм шифрования которого
пока не установлен. Одноразовая передача управления из уже работающего Linux
позволяет проверить своё ядро отдельно от этого формата.

`r36boot` не является полной реализацией стандартного kexec: он предназначен для
однопроцессорной измеренной версии стокового ядра. AVP остаётся запущенным.
Универсальная остановка всех DMA-устройств пока не реализована, что остаётся
возможной причиной неудачи при переключении.

Штатные `vmlinux.uImage`, `avp.uImage`, `dtb.bin` и NOR в этом опыте не меняются.
После полного выключения/включения снова работает штатная загрузочная цепочка.

Старое ядро в RAM не сохраняется как пригодный для возврата образ: новая область
начинается с `0x80100000` и перекрывает его код/данные. Оставшиеся старые страницы
не составляют целого загрузочного ядра. Нынешний loader не сохраняет контекст
старого Linux и не реализует обратный переход. Для возврата без выключения нужен
отдельный пригодный boot-образ и механизм повторной загрузки; дамп работающего
ядра не заменяет его, поскольку ранние init-секции уже могли быть освобождены.

## 3. Сборка диагностического ядра

Из PowerShell:

```powershell
wsl -d ubmips -- bash /mnt/d/r36s-/scripts/kernel_lab/build_kernel.sh
python D:\r36s-\scripts\kernel_lab\build_loader.py
```

Первая команда собирает:

- `vmlinux.elf` — ELF с точкой входа и границами PT_LOAD;
- `vmlinux.bin` — несжатый образ для нашего RAM-загрузчика;
- `vmlinuz.bin` — отдельный сжатый образ; текущий RAM-загрузчик его НЕ использует;
- `r36-lab.dtb` — дерево устройств именно для диагностического опыта;
- `kernel.config`, `System.map`, `manifest.json`.

`manifest.json` проверяет соответствие ELF и raw-образа, содержит адреса и SHA256.
Первый проверенный образ: загрузка `0x80100000`, entry `0x804e4e38`, raw-размер 5 940 192 байта,
размер с BSS 7 209 776 байт. Эти значения относятся к конкретной сборке.
DTB передаётся по адресу `0x82e00000`.

После любой пересборки ядра нужно пересобирать загрузчик: размеры и entry включены
в `image_bounds.h`. Не подменять образ под уже подготовленным старым модулем.

Наш DTS ограничивает память фактически доступной Linux областью, не включает
GPIO/PWM/экран AVP и сохраняет загрузочный pinmux SD. Стандартный DTS автора с
`mem=192M` нельзя напрямую применять к нашему текущему разделению памяти.

## 4. Защита от автосна во время разработки

Установленный TreeFrogUI выбирает профиль GB350, однако адреса nosleep для него
не соответствуют нашему `cubevol`. Защищённый nosleep эти патчи пропускает.

Временная замена при работе:

```sh
sh /mnt/sdcard/cubegm/r36_keepawake.sh start
sh /mnt/sdcard/cubegm/r36_keepawake.sh status
```

Скрипт приостанавливает `cubevol` сигналом STOP и отслеживает новые процессы.
Временно не выполняются его обработчики кнопок, громкости и сна. USB shell
продолжает работать. Это не защищает от разряда аккумулятора.

Вернуть обычную работу:

```sh
sh /mnt/sdcard/cubegm/r36_keepawake.sh stop
```

Скрипт временный: после перезапуска консоли его нужно запускать заново.

## 6. Проверки до переключения ядра

Выполняются в Linux shell консоли:

```sh
insmod /mnt/sdcard/cubegm/r36boot.ko
cat /proc/r36boot
sync
echo 3 > /proc/sys/vm/drop_caches
/mnt/sdcard/cubegm/r36bootctl prepare
/mnt/sdcard/cubegm/r36bootctl status
/mnt/sdcard/cubegm/r36bootctl probe
dmesg | tail -8
```

Ожидаемые результаты, уже проверенные: `idle`, затем `prepared`, return code 0
у `prepare` и `probe`, строки `stock ABI verified` и `uncached trampoline probe rc=0`.

`prepare` выделяет исходные страницы вне всех будущих областей назначения,
строит список копирования, загружает raw-образ и DTB, обнуляет BSS. Во время
подготовки рабочее ядро не перезаписывается. `probe` проверяет вызов короткого
кода через KSEG1 и возвращается в штатное ядро.

Отменить подготовку и освободить страницы:

```sh
/mnt/sdcard/cubegm/r36bootctl cancel
```

В стоке выключена выгрузка модулей: `rmmod` не является способом обновить
загрузчик. Для смены его версии нужен перезапуск консоли.

## 7. Одноразовый запуск: проверенная последовательность

Эта команда прекращает работу текущего Linux и USB MTP:

```sh
sync
/mnt/sdcard/cubegm/r36bootctl boot
```

Загрузчик выключает прерывания CPU, очищает/инвалидирует кэши штатной функцией,
переходит на независимый некэшируемый код, копирует подготовленные страницы и
передаёт управление entry ядра с UHI-регистрами:

- `a0 = -2`;
- `a1 = 0x82e00000` — DTB;
- `a2 = a3 = 0`.

Диагностический init не запускает TreeFrogUI или MTP. Он монтирует devtmpfs,
proc и sysfs, ждёт SD до 60 секунд и пишет отдельный файл:

`/cubegm/r36-own-kernel-proof.txt`

В файле должны находиться `release=7.2.0-rc5-r36lab` и `pid=1`.
Один лишь разрыв USB, зависший экран или успешный `probe` не доказывает загрузку Linux.

В первом опыте Windows продолжает видеть ранее перечисленное USB-устройство
R36S (`VID_18D1&PID_4E22`), но `r36.py info` не отвечает. Сохранённые descriptors
и состояние pull-up также не являются доказательством работы нового ядра.

Для чтения результата после опыта полностью выключить/включить консоль,
дождаться штатного MTP и выполнить на компьютере:

```powershell
python D:\r36s-\scripts\kernel_lab\collect_proof.py
```

Скрипт сохраняет proof, сверяет release/build с локальным raw-образом, проверяет
совпадение файлов ядра/DTB на SD и неизменность штатных boot-файлов. Затем
создаёт JSON с результатом и отмечает проверенный manifest. При новой сборке
`package_kernel.py` снова сбрасывает признак hardware boot: старый результат
не переносится автоматически на новый бинарник.

Перед новым опытом сохранить и удалить старый `r36-own-kernel-proof.txt` с SD,
чтобы его нельзя было принять за результат неудачного повторного запуска.
Если файла нет, следующий этап —
UART-лог или отдельный ранний канал наблюдения; не объявлять запуск успешным.

## 8. Драйверы для штатного Linux 4.4.186

Собственный `r36boot.ko` уже является проверенным работающим модулем этого ядра.
Его особенность — сборка по минимальному ABI, измеренному из штатного `dsc.ko`:

- `struct module`: 320 байт;
- имя модуля: offset 12;
- init: offset 208;
- `struct file_operations`: 108 байт;
- owner/read/unlocked_ioctl: offsets 0/8/32;
- vermagic: `4.4.186-release preempt MIPS32_R2 32BIT `.

`build_loader.py` собирает код MIPS32r2 little-endian, soft-float, no-abicalls,
no-PIC, `-mlong-calls`. Последний флаг нужен для вызова ядра из vmalloc-области
модуля: обычный `jal` не пересекает произвольные 256-МБ области.

Перед применением жёсткого адреса функции cache flush модуль проверяет её первые
16 байт по сохранённому дампу. Это проверка конкретного стока, не универсальный
способ определения совместимости.

Для обычных драйверов предпочтительны точные исходники/конфигурация стокового
ядра и сборка Kbuild. Простая замена vermagic не исправляет layout структур,
набор экспортов или ABI. Здесь точный ABI небольшого модуля измерен отдельно;
эту технику нельзя механически распространять на большой драйвер.

## 9. Драйверы для собственного ядра

Модули 4.4.186 нельзя переносить в Linux 7.2 как готовые бинарники. Драйверы
нужно пересобрать или портировать под выбранное дерево и его API.

В нашем профиле включены `CONFIG_MODULES=y`, `CONFIG_MODULE_UNLOAD=y`;
`CONFIG_MODVERSIONS` выключен. Пример Kbuild внешнего драйвера:

```make
obj-m += my_driver.o
```

```sh
make -C /root/linux-hichip-da5f1a22ef2ff5c46aa3f750fa10825813970b09 \
  ARCH=mips CROSS_COMPILE=mipsel-linux-gnu- M=/absolute/path/to/driver modules
```

Устройство в DTS должно соответствовать `of_match_table` драйвера, его
регистрам, IRQ, clocks и resets. Штатный `dtb.bin` не является автоматически
подходящим DTS для новых upstream-драйверов.

На новом ядре в первую очередь проверять таймер/IRQ, UART, SD и запись proof.
Экран, звук и совместимость с работающим AVP — отдельные этапы после этого.

Практический пример внешнего драйвера находится в
`scripts/kernel_lab/hello_driver/r36hello.c`. Он не обращается к аппаратным
регистрам, выводит сообщения при загрузке/выгрузке и предоставляет read-only
параметр `marker` в `/sys/module/r36hello/parameters/marker`.

```sh
K=/root/linux-hichip-da5f1a22ef2ff5c46aa3f750fa10825813970b09
make -C "$K" ARCH=mips CROSS_COMPILE=mipsel-linux-gnu- modules
make -C "$K" ARCH=mips CROSS_COMPILE=mipsel-linux-gnu- \
  M=/mnt/d/r36s-/scripts/kernel_lab/hello_driver modules
```

Первая команда нужна для получения полного `Module.symvers`, если до этого
собирали только vmlinux. На своём ядре с интерактивным shell:

```sh
insmod r36hello.ko
cat /sys/module/r36hello/parameters/marker
dmesg | tail
rmmod r36hello
```

Первый диагностический init не запускал shell и не загружал этот пример.
Новый профиль ports автоматически вызывает его тест, но успешный результат
на железе ещё не получен.
Пример успешно собран Kbuild; проверен vermagic
`7.2.0-rc5-r36lab mod_unload MIPS32_R2 32BIT `. Артефакт находится рядом с
исходником: `scripts/kernel_lab/hello_driver/r36hello.ko`.
Загрузка/проверка/выгрузка `r36hello.ko` на железе теперь проверена в замороженном
driver-профиле (раздел14). Он предназначен только для
нашего 7.2.0-rc5-r36lab. В штатный 4.4.186 этот файл загружать нельзя.

## 10. Тест освобождения RAM и модулей: отдельный опыт

Первый успешно загруженный комплект сохранён в
`payload/kernel_lab_verified_boot1/`, его свидетельства — в
`analysis/kernel_lab_boot1/`. Текущий `payload/kernel_lab/` содержит новую
тестовую сборку; её результат не следует подменять результатом первой загрузки.

Тестовый init теперь:

1. Сохраняет `/proc/meminfo`, `/proc/iomem` и buddyinfo.
2. Загружает `r36hello.ko`, проверяет sysfs marker, выгружает модуль и проверяет
   исчезновение его sysfs-каталога.
3. Загружает `r36memcheck.ko`, передаёт список страниц старого RAM-загрузчика,
   получает их PageReserved/managed/refcount-статистику и выгружает модуль.
4. Выделяет до 24 МиБ анонимной RAM, оставляя 8 МиБ MemAvailable запаса;
   трижды записывает и проверяет адресно-зависимые шаблоны во всех 32-битных словах.
5. Через `/proc/self/pagemap` считает фактическое повторное использование
   физических страниц, раньше принадлежавших загрузчику.
6. Освобождает выделенную RAM, сохраняет итоговый meminfo, отчёт и kernel log.

Загрузчик дополнен `/proc/r36boot_pages`: после `prepare` его нужно сохранить
до переключения:

```sh
cat /proc/r36boot_pages > /mnt/sdcard/cubegm/r36-reclaim-plan.bin
```

Формат — LE-пары u32 `(адрес KSEG0, признак usable)`, включая пропущенные записи
с нулевым адресом. Для тестового опыта сохранено 2161 записей, из них 1785
уникальных живых страниц; они выровнены и не пересекают будущие области назначения.

Результаты должны появиться в `cubegm/r36-memory-test.txt` и
`cubegm/r36-memory-kmsg.txt`. PASS требует, в частности, нуля ошибок данных и
ненулевого числа страниц загрузчика, реально использованных новым выделением.
Не все прежние страницы обязаны быть свободны одновременно: новое ядро может
использовать их под свои slab, page tables и прочие структуры.

Флаг-файл `cubegm/r36-test-autoreboot` включает попытку сброса после сохранения
отчёта: записи `0xfffffffa` в `0x18818500`, затем `0x26` в `0x18818504`, как в
штатном `board_restart`. Это дополнительный эксперимент, не ранее проверенный
способ возврата. В текущей попытке автоматическое восстановление MTP пока не
наблюдалось; требуется ручной полный перезапуск для чтения отчётов.

После возвращения штатного MTP:

```powershell
python D:\r36s-\scripts\kernel_lab\collect_memory_test.py
```

Скрипт включит keepawake, удалит флаг автоматического сброса, сохранит отчёты,
проверит соответствие proof текущему образу и неизменность штатных boot-файлов.
До получения этих файлов аппаратные результаты теста RAM/модулей неизвестны.

## 11. Текущее портирование аппаратных драйверов

Матрица всех обнаруженных устройств и статусы:
`analysis/driver_port/PORT_MATRIX.ru.md`. Инвентаризация показывает18 AVP-proxy
узлов, зависящих от общего AMPRPC. Полный перенос этого транспорта ещё не завершён.

`build_kernel.sh` теперь поддерживает `LAB_PROFILE`:

- `ports` (по умолчанию): USB CDC/PIO, пассивный ADC IIO, restart handler,
  зарезервированный RAM-журнал и компактный диагностический init;
- `input`: то же плюс GPIO/pinctrl/evdev/serializer и GPIO-кнопки;
- `memory`: прежний тяжёлый init теста RAM и модулей.

Пример отдельной сборки input без замены текущего комплекта ports:

```powershell
wsl -d ubmips -- env LAB_PROFILE=input OUT=/mnt/d/r36s-/payload/kernel_lab_input bash /mnt/d/r36s-/scripts/kernel_lab/build_kernel.sh
$env:R36_KERNEL_OUT = 'D:\r36s-\payload\kernel_lab_input'
python D:\r36s-\scripts\kernel_lab\build_loader.py
Remove-Item Env:R36_KERNEL_OUT
```

Новая команда handoff:

```sh
/mnt/sdcard/cubegm/r36bootctl boot-detached
```

Она отсоединяет старый USB UDC перед переключением. Это важно для прекращения
его DMA; вызов не возвращает старую систему в рабочее состояние после перехода.

Новый init пытается поднять CDC до монтирования SD. Ожидаемые USB IDs:
`1d6b:0104`, serial `R36LAB-PORTS1`. Windows-клиент:

```powershell
python D:\r36s-\scripts\kernel_lab\ports_console.py status --wait 30
python D:\r36s-\scripts\kernel_lab\ports_console.py dmesg
python D:\r36s-\scripts\kernel_lab\ports_console.py driver
```

В первом опыте этого профиля CDC не появилась. Поэтому команды ещё нельзя
считать проверенными на железе. После ручного возврата в сток можно попытаться
прочитать резервный журнал:

```powershell
python D:\r36s-\scripts\kernel_lab\collect_ramconsole.py
```

Он находится в64 КиБ no-map RAM по phys0x02d00000. Переживание физического
выключения не гарантируется; заголовок валидируется перед декодированием.

Первый минимальный запуск до PID1 остаётся подтверждённым, но стабильность
последующих расширенных профилей и перенос всех драйверов пока не подтверждены.

## 12. Автоматический watchdog-reset вместо ручных циклов

В текущем loader добавлен30-секундный watchdog, включаемый ещё в stock до handoff.
Внешний armer защищает окно UDC disconnect, а BOOT ioctl повторно заводит таймер
непосредственно перед переходом. Timeout задаётся `R36_BOOT_TIMEOUT` при сборке.

Проверены автоматический stock-only reset и автоматический возврат из одного
запуска собственного ядра. В следующем расширенном прогоне USB не вернулся;
полная надёжность ещё исследуется. Подробности и свидетельства:
`analysis/driver_port/AUTOREBOOT.ru.md`.

Новый trace перенесён из перезаписываемых64 КиБ на phys0x02f91000 в последний
неполный участок RAM (3584 байта). Его сохранение после watchdog-reset проверено.
Ручной power-off может стереть данные, поэтому при сбоях предпочтителен диагностический reset.

## 13. Готовый офлайн-проверенный комплект перед подключением

Текущая точка входа: `payload/kernel_ready/START.py`.
Она запускает замороженные версии инструментов из `tools/`, проверяет hash
комплекта и исходных ABI-ссылок, ждёт консоль и выполняет два профиля:

1. `boot`: минимальный PID1, SD/vfat, свежий proof с уникальным run_id;
2. `driver`: только после успеха boot — загрузка r36hello, проверка параметра,
   выгрузка и проверка удаления sysfs.

В этих профилях нет USB gadget, ADC, GPIO и физической UART-консоли. Базовая
приёмка изолирована от непроверенных периферийных драйверов. Используются
MIPS Count/Compare, передача DTB через UHI и отдельный RAM trace.

```powershell
python D:\r36s-\payload\kernel_ready\START.py
```

В каждом цикле watchdog настроен на сброс через30 секунд; host ждёт
появления MTP ограниченное время с повторными попытками. Каждый WPD вызов
изолирован отдельным процессом с тайм-аутом. Потеря ответа на handoff не
прерывает ожидание возврата и сбор результата. Следующий профиль не запускается,
если предыдущий не прошёл; дополнительных слепых повторов нет.

Перед прыжком выполняется CRC32 непосредственно по некэшируемым страницам
назначения ядра/BSS/DTB. CRC отличается — stage225 и ожидание watchdog, без
выполнения нового ядра. В `.r36.binding` самого .ko записана проверяемая привязка
к entry, размерам, CRC, DTB, timeout, trace и ABI стока.

Доказательство аппаратного успеха требует одновременно свежего run_id,
соответствия release/build, destination CRC, факта возврата в новый stock boot,
сохранности stock boot-файлов и, для driver, успешной загрузки/выгрузки модуля.
Один лишь разрыв USB или старый proof успехом не считается.

До подключения проверены18 pytest-кейсов,6 эмуляций фактического MIPS-кода,
62 замороженных файла и4 внешние ссылки. Результаты:
`payload/kernel_ready/READY.json`, `offline-tests.xml`,
`boot/emulation.json`, `driver/emulation.json`, `*/preflight.json`.
Hardware acceptance этих конкретных двух образов затем прошла (раздел14).
`READY.json` остаётся неизменяемой записью состояния на момент сборки; аппаратный
результат хранится отдельно в `analysis/kernel_ready_HARDWARE_VERIFIED.json`.

Результаты будущего подключения сохраняются отдельно:
`analysis/acceptance/<номер>/suite.json`; неизменяемый комплект не обновляется
результатами аппаратных тестов.

Повторная подготовка выполняется `scripts/kernel_lab/prepare_bundle.py` без
открытия консоли. Она не перезаписывает существующий готовый комплект; для новой
версии нужно другое имя `--output` под payload. Компилятор запускается с
`-wrapper /usr/bin/env` для обхода воспроизведённого зависания WSL1/vfork.
Для тестовых внешних модулей используется таблица built-in экспортов
`vmlinux.symvers`, без лишней сборки всех in-tree модулей.
