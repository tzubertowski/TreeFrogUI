# Как безопасно модифицировать эту консоль (ядро, загрузчик, драйвер)

Компактный отчёт по итогам локального анализа (дампы SD + SPI NOR) и веб-исследования.
Общее устройство и «что это за железо» — в `analysis/REPORT.md`; здесь только моддинг и риск.

Уровни доказательности:
- **[П]** — проверено на нашей консоли / в наших дампах (SD-образ, NOR-дамп, RAM-дамп);
- **[R]** — подтверждено чужим проектом или открытой документацией (проверяемые ссылки);
- **[?]** — не проверено, гипотеза.

Ключевой внешний источник: **ozkaoz/r36sx-hclinux** (архив) — платформа «свой Linux» для
R36SX V2.6 на том же семействе HiChip HC16xx: своё ядро 5.12.4, свой boot с SD, полный USB-стек,
дважды пережитый и задокументированный окирпич с успешным восстановлением. Это ближайший
проверенный прецедент всего, что описано ниже.

## A. Что можно менять без риска (только SD, NOR не трогаем)

Загрузчик лежит во **внутренней SPI NOR консоли** и читает с карты папку `CUBEGM/`
(path-prefix). Всё, что ниже, — правки файлов на карте; при любом сбое лечится
перезаписью карты из бекапа, консоли ничего не грозит. [П]

**Проверка целостности `CUBEGM/AcXtrnal`** (XOR 0x5A, ~crc32) покрывает ровно **18 файлов**
(сверено с извлечённой копией, `analysis/extract/CUBEGM__AcXtrnal.decoded`):
`rkgame`, `driver.so`, `dtb.bin`, `rootfs/usr/bin/cubevol`, `cubegm/usr/lib/libhcfota.so`,
`cubegm/lib/{ld,libc,libdl,libfreetype,libgcc_s,libm,libpthread,librt,libstdc++,libz}`,
`cubegm/usr/lib/{libpng16,libSDL-1.2,libts}`. **Всё остальное проверкой не покрыто.** [П]

Безопасно (файлы вне списка CRC):
- ROM, обложки, `FILELIST.CSV`/`ALLFILES.LST`, папки систем; утилиты сообщества
  `sync_sd_card` / `download_covers` (LiamJ74). [П/R]
- Темы: `RESOURCE.CPD`, `UI_*.CPD`, `LANGUAGE/*.raw`, `BGM`, звуки, `xgame-logo.bmp`,
  `SETTING.XML`. [П]
- Ядра `CUBEGM/CORES/libemu_*.so`, `CONFIG.XML`, `FILELIST.XML`, биосы `LIB/`. [П]
- Подмена ядра `libemu_md.so` на перехватчик + `<autorun file="…MD/dummy.md"/>` в
  `SETTING.XML` — метод TreeFrogUI; **стоит и работает** (v1.8.0_u, профиль этой консоли). [П]
- Новые файлы/папки (`frogui/`, `roms/`, `MD/`, порты-скрипты). [П]
- Полная перезапись карты из сток-бекапа (см. E) — консоль не страдает. [П/R]

Опасно только на SD-уровне (не кирпич, но «sdcard is damaged» / чёрный экран):
- изменить/заменить любой из 18 файлов `AcXtrnal` (в т.ч. `cubevol` — SF3500-класс
  проверяет его при загрузке; комментарий в `scripts/flash_card.sh` TreeFrogUI); [R]
- удалить/испортить `vmlinux.uImage`, `avp.uImage`, `dtb.bin` — консоль не загрузится
  с этой карты, но NOR цел: перезаписать карту. [П-вывод]

## B. Замена ядра и загрузчика

Цепочка: `BootROM → DDR-init (NOR, 12 288 Б, фабрика) → загрузчик hcboot (NOR, LZMA) →
4 файла с SD из path-prefix-папки: dtb.bin, avp.uImage, vmlinux.uImage, xgame-logo.bmp →
AVP/HCRTOS на втором ядре (дисплей/аудио) → Linux → оболочка`. [R: r36sx BOOT_CHAIN; П: разметка NOR + загрузка с SD]

### Ядро — можно, и без прошивки NOR. Проверено на этом семействе. [R]

- Ядро лежит **на SD** (`CUBEGM/vmlinux.uImage`) и в список CRC не входит → загрузчик
  стоковый грузит с карты то, что туда положено. Проект r36sx-hclinux ставил своё ядро
  **в `cubegm/` стоковой консоли вообще без прошивки NOR** (скрипт `install_own_os.sh`,
  SD-level round-trip бит-в-бит). [R]
- Собранное ими ядро **5.12.4** из SDK (vendor-патчи 0001-0039): полный физический
  PASS — меню, звук, ввод, эмуляторы, видео, выключение. Тулчейн тот же, что у фабрики:
  Codescape `mips-mti-linux-gnu` GCC 6.3.0. [R]
- Мотивация для нас: в стоковом ядре **нет TCP/IP** (нет `inet_init`/`tcp_v4_rcv` в
  kallsyms) [П] — сеть (NCM/USB, telnet, ADB, MTP-надстройки) появляется только со своим
  ядром. r36sx получил NCM + telnet-root + ADB + MTP и интернет через ICS ПК. [R]
- Что нужно для порта на нашу консоль: свой DTS из нашего `dtb.bin` (он на карте
  **plain**, дизассемблируется), board-файлы, патчи vendor из SDK; `avp.uImage` не трогать
  (фабричный AVP обязателен — он держит дисплей и звук). [R]
- Грабли, задокументированные ими: ABI-drift между юзерспейсом фабрики (дек-2025) и SDK
  (июл-2024) — лечится паддингом структур в ядре (ADR-012); vendor `.o`-модули с legacy
  ksymtab 8 Б → «Unknown symbol» при insmod; `insmod` в стоковом ядре уже работает
  (у нас проверено на `usb_f_mtp.ko`). [П/R]
- Стоковое ядро на карте **зашифровано** [П], но r36sx грузит фабричным загрузчиком своё
  обычное uImage [R]. Механизм (расшифровка условная/optional) — смотреть их
  `docs/BOOT_CHAIN.md`; для нас это открытый вопрос №1. [?]

### Загрузчик — не пересобирать. Два реальных окирпичивания. [R]

Пост-мортем r36sx (`docs/experiments/2026-09-20_postmortem-brickeo-bootloader.md`):
1. Свой hcboot c NOR-DTB от ядра → длинная panel-init-sequence вместо короткой фабричной
   → панель не стартует → загрузчик умирает **до чтения SD** → чёрный экран. NOR-DTB
   загрузчика и DTB ядра — разные файлы с разным содержимым.
2. Даже с байт-правильным фабричным NOR-DTB: SDK-собранный hcboot даёт чёрный экран —
   фабрика собрана с другой линией SDK (e3100_cube, дек-2025), фабричный DDR-init в SDK
   отсутствует. Вывод владельца: фабричный загрузчик незаменим доступным SDK.
- Единственный рабочий мод: **7-байтовый патч** распакованного фабричного hcboot
  (`cubegm\0` → `boot\0\0\0`) + пересжатие LZMA с точными параметрами фабрики + прошивка
  через HCProgrammer. Работает, но требует прошивки NOR и нам не нужен — ядро
  меняется на SD. [R]
- MTD на платформе доступен на запись из Linux (r36sx перезаписывал `/dev/mtd1`),
  у нас есть полный дамп — но без нужды не трогать. [R/П]

### AVP (сопроцессор HCRTOS) — не трогать. [R]

Дисплей, аудио, медиа идут через фабричный AVP (amprpc). Свой AVP-firmware не осилил
даже r36sx (парковано, класс риска D). Без нужды не трогать `avp.uImage` и mtd-разметку.

## C. Драйвер — как получить рабочий

- **Рабочий драйвер у нас уже есть.** Расшифрованный из RAM живой консоли
  (`dumpcard/dump_out/file_driver.so`) байт-в-байт совпадает с `driver_sf3500.so` из
  комплекта TreeFrogUI (SHA256 `A3024878…845`). [П]
- Где брать рабочие драйверы: релизы TreeFrogUI (бинарно-патченые расшифрованные стоковые
  драйверы на все профили: r36sx/r36sx27/sf3000/sf3500/gb350); либо дамп из RAM своим же
  tfhijack-методом (уже сделано). Ключ не ломается и не нужен — открытый текст добывается
  из памяти работающей консоли. [П/R]
- Исходники **ядровой** части (fbdev/hcfb, mmz, amprpc, avp-proxy, ge = 2D-движок, musb,
  i2c, spi, pinctrl и т.д.) — в SDK `hcdrivers` (см. D/E). [R]
- Исходников юзерспейсного `driver.so` в открытых источниках нет — он только бинарно
  патчится (замена строк путей `cubegm`→`tf`, null-padding). Для своей графики его можно
  вообще не трогать: рисование через `/dev/fb1` + `/dev/dis` из своего кода. [R]
- Нюанс идентификации: панель по DTB 640×480, а расшифрованный драйвер — класса SF3500;
  фактически установленная конфигурация TreeFrogUI работает. Для модификаций дисплея
  опираться на наш `dtb.bin`. [П]

## D. Кирпич и восстановление

**Что реально окирпичивает** — только запись во внутреннюю SPI NOR (512 КБ, разметка
проверена нашим дампом: `nor` 0x80000 = `boot` 0x61000 + `dtb` 0x9000 + `eromfs` 0x6000 +
`persistentmem` 0x10000). Штатный путь — `USR/BIN/HCFOTA` (режимы sd/usbhost/network);
файлы HCFOTA из неизвестных источников не прошивать. [П/R]

Степени «кирпича»:
1. **Битая SD** (CRC, удалён boot-файл): консоль цела. Лечение — перезапись карты из
   бекапа. У нас: полный образ `backup/r36s_sd_16gb.img` + расшифрованные
   `driver.so`/`rkgame` + дампы NOR/ядра. [П]
2. **Мёртвый загрузчик** (чёрный экран, NOR побит) — задокументированное восстановление
   без замены чипа [R]:
   - **Короткое замыкание пинов 2/4** SOP-8 флеша (pin2 = MISO → GND = pin4; pin 1 —
     точка, отсчёт вниз по левому краю), консоль выключена, USB-C подключён к ПК;
   - включить с замыканием → BootROM не может прочитать NOR → USB-режим blank-chip,
     Windows видит «HiChip 16xx USB Device» (драйвер `HiChip16xxUSB.inf` из SDK);
   - запустить **оба** `HCProgram.exe` и `HCProgrammer.exe` одновременно (иначе не
     детектится), Firmware select = **HCFOTA.bin** (не сырой дамп!), Start Burn;
   - формат HCFOTA генерит `HCFota_Generator`: `-r ddrinit.abs -p hc16xx_jtag_updater.bin`
     + секции NOR; сырой `spinorflash.bin` тул не принимает;
   - перезагрузка → фабричный загрузчик. Проверено дважды, ~10 минут на операцию.
   - Альтернатива: программатор **CH341A + клип SOP-8**, залить наш полный образ NOR
     (512 КБ, есть в `analysis/kdump_card2/`). [П-дамп/R-метод]
3. **Живой загрузчик**: HCProgrammer опрашивает USB прямо перед запуском ядра
   (~300 мс окно) — прошивка возможна без разборки консоли. [R]

Правила выживания:
- Восстанавливать ТОЛЬКО из собственного дампа или побайтно сверенного бекапа той же
  модели: `persistentmem` содержит данные устройства. [? — осторожно]
- Перед любым экспериментом с NOR: полный дамп (уже есть) + проверка, что окно
  BootROM-USB живо (замыкание 2/4 детектится). [R]
- Ядро менять только на SD-уровне; загрузчик/DDR-init/AVP не пересобирать (см. B).

## Открытые вопросы

1. Примет ли фабричный загрузчик нашей модели незашифрованное uImage (как у R36SX) —
   смотреть `docs/BOOT_CHAIN.md` r36sx; дамп расшифрованного ядра из RAM у нас не снимался.
2. Точное соответствие модель/панель (640×480 DTB + драйвер класса SF3500) — сверить
   `dtb.bin` со сток-бекапами из H.OS_stock_backup (ПК-работа, без записи на карту).
3. Публичное размещение SDK hclinux-2024.02.y.2 — не найдено (нужен автор r36sx-hclinux
   или HiChip FAE).
4. Поведение AcXtrnal на изменённый файл на нашей консоли: ожидание «sdcard is damaged»
   подтверждено чужим кодом, не нашим тестом. [R]
