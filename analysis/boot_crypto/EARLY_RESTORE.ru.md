# Раннее восстановление загрузочного файла до Linux

## Аппаратный результат

На консоли проверено восстановление `cubegm/advapi32.dll` средствами живого
NOR-загрузчика **до входа в штатный Linux 4.4**. Сам Linux 7 в этих испытаниях
не запускался. Тестовый образ содержит неизменённые распакованные байты stock
ядра и добавленный MIPS-зонд в конце; при возврате из зонда используется исходный
entry `0x803337c0`.

Авторитетный receipt:
`analysis/boot_crypto/kernel_loader_early_restore_probe_v1_trial.json`.

- Session tag: `0xbd6eb903`, trace stage202.
- Прочитано, записано и перечитано:3954299 байт.
- CRC32 исходника и результата: `0xc3693b14`.
- После возвращения USB MD5 target: `3510ffdfd039f850345ace1489572659`.
- `stock_already_restored_before_host_cleanup=true`.
- `host_cleanup_wrote_boot_file=false`: ПК не выполнял восстановительную запись.

Загрузочный файл уже исходный. Сохранённый encrypted original на ПК:
`analysis/boot_crypto/original_advapi32.dll`.

## Что проверено последовательно

1. Преднамеренное ожидание watchdog до перезапуска. Повторная загрузка распознала
   pending-метку и пропустила действие, затем запустила stock. Аппаратный stage197,
   tag `0x365938bb`; ручной перезапуск не понадобился.
2. Чтение64 байт sandbox-файла через loader resolve/open/read/close. Stage195,
   tag `0x549fd903`, данные совпали полностью.
3. Запись64 байт в существующий отдельный файл, FAT sync, close, повторное чтение.
   Stage200, tag `0xa6586e83`; MD5 файла проверен после старта Linux.
4. Полная копия encrypted stock-контейнера в `R36COPY.BIN`. Stage203,
   tag `0x8736e1bf`; оба CRC и последующий MD5 совпали.
5. Та же полная процедура для настоящего `advapi32.dll`, stage202/tag `0xbd6eb903`.

Receipts имеют имена `kernel_loader_*_trial.json`; рядом сохранены сырые `.trace.bin`
и `.runtime.txt`. В первом full-copy receipt ошибка смещения полей CRC в декодере
исправлена по первоначальному бинарному следу без повторного аппаратного теста.
Запись `decoder_correction` сохраняет это обстоятельство. Отладочные области,
которые конкретный вариант зонда не заполнял, больше не интерпретируются.

## Выясненные особенности loader API

- Resolver `0x89da9130` при flag0 по `0x89e5f168` принимает только имена из таблицы
  Windows-алиасов. Неизвестное имя возвращает ошибку ещё до поиска файла.
  Для sandbox/backup вызова flag временно устанавливается1 и затем восстанавливается.
- В данном boot namespace реальная найденная строка была
  `/media/mmcblk0p2/cubegm/R36PROBE.BIN`. Это имя mountpoint внутри загрузчика;
  Linux продолжает использовать `/dev/mmcblk0p1`. Пути не нужно хардкодить.
- Перед kernel entry loader маскирует контроллер прерываний и входит в critical
  section. Зонд возвращает сохранённые mask/shadow значения, выходит из вложенных
  critical sections и после I/O восстанавливает глубину и маскирует IRQ обратно.
  В аппаратном следе Status: `0x11000900 -> 0x11000901 -> 0x11000900`, depth1.
  В эмуляции отдельно проверены depth3 и отказ при неподдерживаемом контексте.
- Open `0x89ddce88`, read `0x89ddd374`, write `0x89dddb60`, close `0x89dde110`.
  Get-file-pointer `0x89dde004`, FAT sync `0x89de0a80`.
- Первые16 байт каждого вызываемого API сверяются с идентифицированным TPL.
  Несовпадение даёт stage198 без вызова файловых функций.

## Порядок восстановления

`scripts/boot_crypto/loader_fs_probe.py` генерирует код:

1. Инициализировать trace с уникальным tag и поставить watchdog30с.
2. Проверить API/context, временно возобновить loader I/O.
3. Найти `R36STOCK.ENC`, полностью считать в scratch `0x81000000`, проверить точный
   размер, EOF и CRC. Неверный/короткий backup не приводит к записи target.
4. Открыть существующий target `O_RDWR`, без создания и усечения. Записать исходник
   порциями до64KiB с обработкой положительного partial I/O и обновлением watchdog.
5. Выполнить FAT sync и close, открыть target снова, полностью перечитать и сверить
   размер/EOF/CRC; только после этого выставить stage202 и phase6.
6. Восстановить loader interrupt context и перейти в неизменённый stock kernel.

Тестовый boot-контейнер имеет **ровно исходную длину3954299B**. Недостающие байты
добавлены внутрь encrypted plaintext после завершённого uImage payload. Родной
bootm/gzip принимает такой контейнер; лишние plaintext bytes не входят в uImage
data CRC и не исполняются. Размер FAT-файла при восстановлении остаётся прежним,
усечение и переименование не используются. Отключение питания во время записи
отдельно не испытывалось.

## Проверки на ПК

- Оригинальные MIPS critical/mask helpers исполняются в Unicorn; файловые API там
  являются stubs. Проверяются возврат аргументов/регистров, IRQ state, pending-gate,
  несовпадение API, ошибки resolve/open/read/write/sync/close и CRC/EOF.
-23 сценария с65537B (пересечение границы64KiB), включая успешный partial I/O.
- Отдельный полный проход3954299B с исполнением MIPS CRC обоих буферов.
- Родные bootm header/CRC и gzip также исполняются в эмуляторе.
- Эмуляция не заменяет аппаратные receipts выше.

## Интеграция Linux 7 выполнена

Обновление после подготовки этого документа: native stock fallback аппаратно
проверен, затем `kernel_cold_early_restore_v1` выполнил прямой NOR-start Linux7
до PID1/SD proof и автоматически вернулся в stock. ПК не переписывал boot-файл.
См. `COLD_BOOT.ru.md` и `kernel_cold_early_restore_v1_trial_VERIFIED.json`.
Проверка выполнена через watchdog-reset, не через полный power-off/on.

Исторический план интеграции (теперь выполнен):

Ранний откат аппаратно готов, но в Linux7-кандидат ещё не встроен. Текущий зонд
при ошибке прыгает в stock entry, потому что исходный Linux4.4 есть в его payload.
Такой error branch **нельзя напрямую переносить** в образ, где адреса stock уже
заняты Linux7.

Для следующего кандидата нужно отдельно реализовать/проверить stock fallback через
load/decrypt/bootm backup-файла либо эквивалентное размещение fallback-кода и данных.
Нормальный путь должен проверять раннее восстановление, затем входить в Linux7
напрямую из NOR. После этого зависание Linux7 сможет вернуть исходный SD-образ по
watchdog без работы нового PID1. Для первого такого теста предпочтителен frozen
boot profile с уже проверенным встроенным initramfs и неизменённым DTB; SD-root
glibc/BusyBox маршрут старого неудачного кандидата пока не имеет аппаратного PASS.

Frozen `payload/kernel_ready` не изменялся. Точный старый сбой Linux7 по-прежнему
не локализован: его trace утрачен после power-cycle. Low-RAM shim fix по0x80010000
остаётся отдельным подтверждённым исправлением условной boot-wait зависимости.
