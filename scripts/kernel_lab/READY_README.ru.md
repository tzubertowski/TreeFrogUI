# Подготовленный диагностический комплект

Запуск с компьютера:

```powershell
python D:\r36s-\payload\kernel_ready\START.py
```

Затем подключить включённую консоль в штатном USB/MTP-режиме. Сценарий ждёт
подключения до180 секунд. Штатная версия:4.4.186-release #23, 27 января2026.

## Что выполняется автоматически

1. Повторная проверка целостности всего комплекта и версии стока.
2. Проверка штатных boot-файлов, доставка инструментов, отключение автосна.
3. При необходимости сброс ранее загруженного диагностического модуля.
4. Минимальный тест boot: новое ядро, свой PID1, запись свежего proof на SD.
5. Аппаратный watchdog-reset через30 секунд и ожидание возвращения штатного MTP.
6. Проверка trace/CRC/proof и неизменности штатных boot-файлов.
7. Только после успеха boot — такой же цикл driver с загрузкой/выгрузкой r36hello.ko.

Результаты находятся в `D:\r36s-\analysis\acceptance\<номер запуска>\`.
При ошибке дальнейшие загрузки прекращаются, а отчёт сохраняется. Каждый вызов
WPD выполняется в отдельном процессе с тайм-аутом; бесконечного ожидания USB нет.

## Что проверено до подключения

`READY.json`: результаты offline-проверок и hash bundle.json.
`boot/preflight.json`, `driver/preflight.json`: ELF/ABI/DTB/config/initramfs.
`boot/emulation.json`, `driver/emulation.json`: реальный машинный код relocation
и kernel head в MIPS74K-эмуляторе, в том числе повреждение исходной страницы.
`offline-tests.xml`: проверки отказов сценария, устаревшего proof, нарушения CRC,
неверной прошивки, зависания WPD и ошибки выгрузки драйвера.

CRC после фактического копирования проверяется в некэшируемом relocation-коде.
При несовпадении ядро не запускается; управление остаётся watchdog.

## Границы готовности

Это проверенный на компьютере **диагностический комплект**, а не подтверждённая
полноценная игровая прошивка. Физическая приёмка именно этих двух новых образов
ещё должна пройти. Эмулятор не моделирует реальные DMA, кэши и MMIO HC16E310.

USB CDC, ADC, GPIO, экран и звук намеренно не включены в первые два теста.
Их перенос продолжается отдельно после подтверждения базового запуска.
Образы stock Linux/AVP/DTB и NOR сценарий не заменяет.

При аппаратном сбое, который останавливает сам watchdog или штатную загрузку,
физическое восстановление всё ещё может потребоваться. Ранее подтверждены
stock watchdog-reset и один автоматический возврат из нового kernel_entry;
стабильность расширенных профилей пока не подтверждена.
